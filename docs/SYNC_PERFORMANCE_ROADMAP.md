# ONI Together 实时联机与同步性能路线图

更新日期：2026-07-13

源码基线：`9a7aca573f22e02bae6bd115abdc034cc08ab1f3`。后续 `fe6b2ef9abe7d0b44bbc827e90e5010500a3949e` 只修改维护规则，Mod 源码未变化。

## 范围

唯一目标是让 2–4 位可信朋友能够真正、流畅、实时地共同操作同一个殖民地：

- 玩家操作尽快得到主机权威结果；
- 光标、小人、动画、任务、建筑和世界状态连续可见；
- 丢包、乱序、延迟和短暂断线不会形成永久分叉；
- 大殖民地与 Hard Sync 不应造成严重卡顿；
- U59 新玩法纳入明确同步覆盖。

账号认证、权限、反作弊、对抗性客户端、玩家资产归属和独立物品不在范围内。

详细证据：

- `docs/audits/2026-07-13-sync-correctness.md`
- `docs/audits/2026-07-13-network-performance.md`
- `docs/audits/2026-07-13-gameplay-sync-coverage.md`

这些结论均为静态代码审计；在取得 U59 程序集并完成兼容编译、双实例和故障注入前，不宣称运行时复现或修复完成。

## 总体判断

现有实现已经具备相当多的合作玩法入口，但不是锁步模拟。它采用：

1. 主机权威模拟；
2. 玩家工具和侧栏操作的事件包；
3. 小人、动画、建筑、世界格子等周期状态包；
4. viewport 裁剪和 bulk 聚合；
5. 加入或严重分叉时传输完整存档并 Hard Sync。

当前最大问题不是“是否有同步代码”，而是多个同步域缺少统一的 epoch、revision、顺序、确认和自愈语义。Unreliable 包丢失或乱序后，部分客户端会永久停留在旧状态；Hard Sync 本身也不是严格的原子事务。

## P0：先解决“能不能稳定一起玩”

### P0-1：统一会话时序模型

引入并贯穿所有重要协议：

- `sessionEpoch`：一次多人会话/重载代次；
- `syncEpoch`：一次 Hard Sync 或完整快照代次；
- `hostTick`：主机单调模拟时间；
- `commandId`：玩家操作唯一编号；
- `stateRevision`：实体、格子、网络或快照的单调版本。

客户端必须拒绝旧 epoch 和旧 revision，不能让晚到的旧包覆盖新状态。

### P0-2：重构 Hard Sync 为 ACK 驱动事务

当前问题：

- 每位客户端可能分别生成不同时间点的存档；
- Hard Sync 期间仍可能发生世界写操作；
- 结束时间靠估算，不等待真实下载、加载和重连；
- `HardSyncCompletePacket` 没有发送点；
- 客户端断线可能永久卡住 Ready barrier。

目标流程：

1. 主机冻结或记录写操作；
2. 只生成一次带 `syncEpoch` 的不可变快照；
3. 同一快照发送所有客户端；
4. 客户端依次确认 `downloaded → verified → loaded → reconnected → applied`；
5. barrier 只统计仍有效连接；
6. 全部完成后广播明确的完成消息并恢复速度；
7. 失败客户端可跳过、重试或重新加入，不阻塞全局。

### P0-3：修复存档传输代次与背压

必须修复：

- 传输 ID 不能由文件名固定生成；
- 客户端组装 key 必须包含客户端、文件和 epoch；
- 新传输开始时取消旧 coroutine、ACK 和组装状态；
- 完整文件验证长度和哈希；
- LAN 优先使用现有 TCP 文件通道；
- UDP fallback 使用有限在途窗口、累计/位图 ACK 和 RTT/RTO；
- Steam 只使用一层可靠机制，避免 transport reliable 与应用 ACK 重复；
- 不允许每帧无背压突发约 512 KiB 阻塞实时操作。

### P0-4：修复 LAN 大包分片

当前 `ChunkedPacket`：

- 只按本地 sequence 聚合；
- 不包含发送连接和 epoch；
- 丢片后不重传；
- 没有超时、内存上限和清理；
- 多客户端 sequence 可碰撞串包。

目标：

- key 至少为 `(connection, sessionEpoch, sequence)`；
- 可靠大消息支持完整性、超时和重传；
- 不可靠状态不能依赖“所有分片都到齐才应用”的巨型消息；
- 状态列表应拆成 MTU 内、可独立应用、带 revision 的分页。

### P0-5：普通断线自动恢复

当前通用自动重连调用被注释，瞬时网络波动会退出世界。

目标：

1. 有界指数退避；
2. 重连后请求当前 epoch 和最后 revision；
3. 能补增量则补增量；
4. 无法补齐时自动进入 Hard Sync；
5. 重连期间冻结本地写入但保留世界和 UI，不直接退回标题。

### P0-6：建立 U59 兼容基线

仓库声明目标为 `U57-700386`，当前正式游戏为 `U59-740622`。取得合法程序集后，在 8ka：

- Publicize U59 程序集；
- 修复编译和 Harmony 目标；
- 盘点新 NavType、creature、plant、workable、building/component；
- 建立 U59 水生玩法的同步矩阵；
- 所有构建、测试和游戏实例只在 8ka 执行。

## P1：消除永久分叉和明显错误

### P1-1：世界格子状态自愈

当前 shadow 主要跟踪元素和质量，纯温度与病菌变化可能长期不发；发送 Unreliable 后立即推进 shadow，最后一包丢失可能永久错误。

修复方向：

- shadow 纳入温度和病菌；
- 每批或每 chunk 带 revision；
- 可见区域定期发送权威全状态，不只 delta；
- 客户端拒绝旧 revision；
- 低 FPS 时优先保留当前 viewport，同步降级只影响后台扫描。

### P1-2：管道与运输

- 强制刷新必须明确发送空管状态，消除幽灵液体/气体；
- 用管道 dirty set 代替每 1.5 秒全地图扫描；
- 按每位客户端 viewport 分桶发送，不能“任意人可见后广播所有人”；
- 增加 `SolidConduitFlow`/运输轨道同步。

### P1-3：自动化和结构 stale repair

当前客户端 stale request 被 `SessionHasPlayers > 1` 条件错误阻断。

修复方向：

- 客户端连接主机与本地玩家计数分离；
- 进入 viewport 时主机主动发送可靠完整状态；
- 自动化加入网络/端口值与拓扑快照；
- 结构状态由集中式 registry 分片 tick，减少每建筑 `Update()`。

### P1-4：玩家工具改为主机权威命令流

当前部分操作是来源客户端先本地执行，主机再无条件转发。并发建造、取消、拆除可能各端结果不同。

目标：

1. 客户端发送 intent；
2. 主机基于 world revision 验证；
3. 主机执行并广播 `commandId/result/newRevision`；
4. 客户端预测必须可以提交或回滚；
5. 建筑创建、完成和删除保持幂等。

### P1-5：建筑拓扑 reconciliation

- 恢复或重做当前未启用的 `BuildingSyncer`；
- 快照包含 NetId、cell、layer、prefab、朝向、材料、facade、温度和 revision；
- 权威 tombstone 删除客户端幽灵建筑；
- 缺失 ghost 时也能幂等创建完工建筑；
- 低频快照按 chunk 分帧执行，避免每 30 秒卡顿尖峰。

### P1-6：资源、地面物品与库存

`ResourceSyncer.Update()` 当前被硬 `return` 禁用，是明显玩家可见缺口。

需要：

- 启用主机权威资源统计；
- 校正资源栏与实际库存；
- 覆盖地面物品质量、温度、病菌、腐败、堆叠拆分/合并和位置；
- 区分纯视觉搬运代理与真实实体库存。

### P1-7：动物、装备和技能语义状态

增加周期或事件+快照覆盖：

- 动物：生命、年龄、饥饿、驯化、幸福度、繁殖、蛋、捕捉和死亡；
- 装备：装备槽、服装/气压服 prefab、耐久、储氧、燃料和属性；
- 技能：已掌握技能、技能点、经验、士气需求、帽子和洗点。

## P2：实时观感和联机性能

### P2-1：位置与动画插值

- 修复 Unix 时间与 `Time.unscaledTime` 混用导致 stale request 永不触发；
- 使用 10–20 Hz 带 sequence/host tick 的位置快照；
- 客户端保留 2–3 个样本，使用约 80–120 ms 插值缓冲；
- 短丢包时有限外推，恢复后平滑纠偏；
- 动画按 host tick 和估算延迟推进相位，拒绝旧包，避免周期回跳。

### P2-2：光标

- 移动时维持约 10–15 Hz；
- 静止时降为约 1 Hz；
- viewport、工具和 utility path 只在变化时发送；
- 使用持续插值器，不为每个包停止并重启 coroutine。

### P2-3：主线程网络预算

- LAN 和 Steam 统一按毫秒预算处理入站消息；
- 光标、位置和工具命令优先；
- 全量 reconcile 分帧；
- 同实体陈旧状态在入队前合并；
- `MainThreadExecutor` 改为线程安全队列，每帧在 1–2 ms 预算内 drain；
- 下载进度使用最新值覆盖，完成/错误事件高优先级。

### P2-4：减少分配、反射与重复序列化

- Packet 注册时缓存构造委托，避免每包 `Activator.CreateInstance`；
- 复用 Steam poll 数组与 buffer；
- 广播包序列化一次，多连接复用；
- 使用池化 writer/buffer，避免 `ToArray` 和非托管分配；
- `PacketTracker` 默认只保留类型、大小、时间和计数，不持有 100,000 个完整 payload；
- 配置值缓存，避免每帧反射读取。

### P2-5：真正的 interest management

以客户端 chunk subscription 为中心：

- 每帧只计算一次本地 viewport；
- 合并重叠 viewport；
- 同一 chunk 每 tick 序列化一次；
- 只发给订阅该 chunk 的客户端；
- 进入 viewport 时发送完整 chunk snapshot；
- 离开后停止增量；
- world、conduit、status、plant、building 使用同一 interest manager。

### P2-6：集中式同步调度

把每实体/每建筑 `Update()` 改为 registry + dirty set + 真正 shard：

- 位置实体只维护活跃移动集合；
- 动画每 tick 真正只遍历一个 shard；
- Logic 注册时确定 adapter 并缓存组件；
- 管道、建筑、植物按事件标脏；
- 心跳只做低频自愈。

## 必须建立的双实例验证矩阵

### 实时操作

- 两名客户端同格并发建造、取消、拆除和改优先级；
- 光标、框选、建筑预览、管线路径；
- 暂停与倍速竞争；
- 挖掘、拖地、收获、复制设置和侧栏参数。

### 小人与玩法

- 行走、梯子、游泳、工作、搬运、睡眠、吃饭、死亡；
- 任务列表、工作进度、vitals、effects；
- 技能学习、连续升级和洗点；
- 气压服穿脱、氧量、耐久和燃料；
- 牧场、抽液站、装瓶、冰壶、望远镜等特殊 workable。

### 世界与系统

- 纯温度变化和纯病菌变化；
- 管道排空、桥接、过滤、储罐和跨世界管道；
- 固体运输轨道；
- 电线、变压器、负载、过载和 smart battery；
- 自动化网络和 ribbon；
- 资源栏、地面物品、容器、腐败和堆叠变化；
- 植物生长、枯萎、施肥和变异；
- 动物出生、饥饿、驯化、繁殖、蛋和死亡；
- 全部 U59 水生实体、建筑、植物、任务和游泳路径。

### 网络故障

- 固定延迟、抖动、乱序、重复和丢包；
- 丢失最后一个 Unreliable 状态包；
- 大包任意分片丢失；
- Hard Sync 中途继续操作；
- Hard Sync 中客户端断线；
- 两次存档传输交叠；
- 短时断网自动重连；
- 新客户端进入此前无人观察的 viewport。

## 性能验收指标

在运行实测前先采集基线，不凭静态估算宣称达标。至少记录：

- 主机/客户端 FPS 和 95/99 分位帧时间；
- 主线程网络处理毫秒数；
- 每秒收发字节、包数及可靠队列年龄；
- 丢包、重传、乱序和被合并的陈旧状态数量；
- 每秒托管分配和 GC pause；
- 每同步域的发送频率、payload 大小和 catch-up 时间；
- 加入与 Hard Sync 的快照生成、下载、加载和 Ready barrier 时间；
- 主客关键状态哈希与首次分叉时间。

测试规模至少覆盖：

- 2人小型殖民地；
- 4人中大型殖民地；
- 玩家视野集中；
- 玩家视野分散；
- Steam transport；
- LAN transport；
- 正常网络与故障注入网络。
